## 2. The rubric (hard-coded, identical for both pairs)

Raw values are the **event-mean** measured metrics (`{key}_event_mean` of
`part2_driving_style.per_pair`), exactly the quantities fig_06 already plots.
`score = 0` is worst/physically unacceptable, `score = 1` is ideal.

```
axis (metric key)                          anchors: raw value -> score
efficiency (moving_fraction)               0 -> 0, 1 -> 1
gap keeping (spacing_mean_m)               5 -> 0, 10 -> 1, 25 -> 1, 40 -> 0
closest approach (spacing_min_m)           2 -> 0, 6 -> 1
smoothness (jerk_rms_smoothed_mps3)        0.5 -> 1, 3 -> 0
comfort (accel_rms_mps2)                   0.5 -> 1, 3 -> 0
```

`rubric_score(value, anchors)` sorts the breakpoints, linearly interpolates between the
two that surround `value`, clamps outside them to the outermost anchor score, and clamps
the result to `[0, 1]`. The breakpoints are **not** required to be monotone in score —
`gap keeping` is a window merit (rises 5→10 m, plateaus, falls 25→40 m). Score `1.0` is
therefore reached on a *plateau* that belongs to the anchor set alone
(`jerk/accel: x <= 0.5`; `closest approach: x >= 6`; `gap keeping: 10 <= x <= 25`), never
because a value happens to be the larger of the two datasets. A missing / `None` / NaN /
±inf value scores `0.0` (worst) instead of raising, so an absent metric can never look
better than a measured one. The helper takes no other dataset and no statistic of the
data, which is what makes the scale third-dataset-safe.

## 5. Assumptions, deviations, remaining issues

1. **Anchor saturation is visible and expected.** Because the anchors are fixed by the
   brief, none was tuned to the data: both pairs' jerk RMS (0.377 / 0.335 m/s³) and accel
   RMS (0.381 / 0.337 m/s²) sit below the 0.5 m/s³ / 0.5 m/s² ideal anchor, so those two
   axes are legitimately 1.0 for both pairs, and HV-AV additionally saturates on gap
   keeping and closest approach. The radar therefore separates the pairs only on
   efficiency (0.7550 vs 0.7806), gap keeping (0.7010 vs 1.0000) and closest approach
   (0.5596 vs 1.0000). This is the honest consequence of the requested rubric, not a
   normalisation artefact: the same numbers appear when each pair is scored alone.
2. The title and the radial-axis label carry the en dash (`0–1`) exactly as in the brief.
   It is written as `"\u2013"` in the source (ASCII-safe escapes) and renders correctly in
   DejaVu Sans — verified on the PNG.
3. The radial axis carries the label `score (0–1)` *in addition to* the five required axis
   titles, since the brief asks the titles to say "score (0–1)" rather than "inverse …";
   no "inverse …" wording remains anywhere in the repository (grep for `pair maximum`,
   `normalised to the pair`, `inverse jerk`, `inverse accel` matches only the brief itself).
4. `figure_style()` now returns the score rows (the radar table) instead of `None`; the
   only caller is `main()`, so no other code path is affected.
5. The script still regenerates all eleven figures per run (unchanged design); that is why
   the mtime of the other ten PNGs moves even though their bytes do not. If a
   "touch-only-fig_09" run is wanted later, the `figure_style(...)` call can be invoked on
   its own — not implemented, to avoid adding an unrequested CLI switch.
6. The two self-contained HTML reports (`results/lab1_full_report.html`,
   `results/lab1_template_report.html`) are **not** regenerated and contain no reference to
   `fig_09` or to the old normalisation wording (checked with grep), so nothing there is
   stale.
